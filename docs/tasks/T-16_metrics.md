# T-16 监控指标埋点

| 项 | 内容 |
| --- | --- |
| 阶段 | P4 |
| 依赖前置 | T-02 |
| 产出 | Prometheus 指标、结构化事件、告警规则、看板、慢查询采集 |
| 验收门 | 6 类核心指标可查；告警分级生效；看板可展示 P95 |
| 预估工作量 | 4 人日 / 3 卡 |
| 人工主导 | 是（人工主导：告警阈值与值班表待业主定） |
| 外部阻塞 | 阻塞于 C-02（并发与业务量）、C-16（RPO/RTO 仅备份相关） |

## 1. 目标

让“系统慢、队列堵、推理挂”在上报之前就被看到。

## 2. 输入

- V1.2 §14.1 指标清单
- FastAPI 中间件
- Redis/PostgreSQL/MinIO 探针

## 3. 改动范围

- 允许：backend/app/core/metrics.py、deploy/prometheus/**
- 禁止：在业务逻辑里写裸打点字符串

超出上述范围即视为越权改动，即使代码正确也退回。

## 4. 实现要点

- 指标命名 `bt_<domain>_<metric>_<unit>`，如 `bt_api_request_p95_ms`
- 必须采集：API P95、错误率、队列积压、推理耗时/QPS、点云瓦片命中率、存储水位、DB 连接与慢查询
- 告警三级 P1/P2/P3，P1 电话、P2 群消息、P3 日报
- traceId 与指标关联，可从慢请求跳到日志

## 5. DoD（可验证的完成定义）

- /metrics 暴露且被 Prometheus 抓取成功
- 注入 100 次 500 错误后错误率指标上升
- 慢查询 > 1 s 被记录并可查
- 告警规则触发一次并在恢复后自动关闭

## 6. 验收用例

| # | 输入 | 操作 | 期望结果 |
| --- | --- | --- | --- |
| 1 | 人为制造队列积压 500 | 观察 | `bt_queue_backlog` > 阈值并触发 P2 |
| 2 | 推理服务返回 503 | 调用 | 错误率与依赖可用性指标同时变化 |
| 3 | 数据库连接池打满 | 压测 | 触发 P1 并记录当前连接数 |

## 7. 依赖与顺序

T-02 之后即可开始，T-24 灰度依赖它判断回滚。

## 8. 常见坑

- 不要用高基数标签（用户 ID、工单号）
- 不要在请求路径同步写远程监控
- 不要只采集平均值，要 P95/P99
