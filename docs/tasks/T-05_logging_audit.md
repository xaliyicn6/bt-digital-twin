# T-05 日志与审计

| 项 | 内容 |
| --- | --- |
| 阶段 | P1 |
| 依赖前置 | T-02 |
| 产出 | 结构化日志规范、traceId 贯通、审计哈希链、脱敏过滤器、日志查询接口 |
| 验收门 | 审计记录不可改；日志字段齐全；脱敏规则生效 |
| 预估工作量 | 4 人日 / 3 卡 |
| 人工主导 | 是（人工主导：留存期与脱敏范围需确认） |
| 外部阻塞 | 阻塞于 C-15（日志与审计留存期，默认 H-05） |

## 1. 目标

让每一次登录、导出、缺陷确认、工单流转都可回溯到人、时间与对象。

## 2. 输入

- V1.2 第 12 章
- audit_log 表
- H-05 留存：应用日志 30 天热 + 180 天冷；审计 ≥3 年

## 3. 改动范围

- 允许：backend/app/core/logging.py、modules/audit/**、core/masking.py
- 禁止：业务模块自行拼日志字符串

超出上述范围即视为越权改动，即使代码正确也退回。

## 4. 实现要点

- 日志字段固定：traceId、userId、module、action、objectId、result、costMs、errorCode
- 审计只追加：`prev_hash` + `hash` 组成链，任何 update 由触发器拒绝
- 脱敏：手机号/身份证中间四位，人脸与车牌在导出时打码
- 点云与影像的下载、预览也要记审计，不只记导出

## 5. DoD（可验证的完成定义）

- 任一请求的日志可按 traceId 串起 3 层调用
- 直接 UPDATE audit_log 被触发器拒绝
- 导出含人脸的影像时输出已打码
- 审计查询接口按角色限权且自身也记审计

## 6. 验收用例

| # | 输入 | 操作 | 期望结果 |
| --- | --- | --- | --- |
| 1 | 确认缺陷 | POST /defects/candidates/{id}/confirm | audit_log 新增一条，prev_hash 指向上一条 hash |
| 2 | 直接 SQL 改 audit_log.detail | UPDATE | 触发器抛异常，事务回滚 |
| 3 | 导出含车牌影像 | POST /exports | 输出文件车牌区域已模糊，审计记录 masking=plate |

## 7. 依赖与顺序

T-02 之后即可做，早于所有业务卡，避免后期补日志。

## 8. 常见坑

- 不要用 print 调试后留在代码里
- 不要记录完整 token 或口令
- 审计写入失败不得静默，业务应回滚
