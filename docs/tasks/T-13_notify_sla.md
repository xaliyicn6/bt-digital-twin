# T-13 通知与超期升级

| 项 | 内容 |
| --- | --- |
| 阶段 | P3 |
| 依赖前置 | T-07 |
| 产出 | 站内通知、超期三级升级、通知重试、免打扰与聚合 |
| 验收门 | 超时 0-24h 通知本人与主管；24-72h 上报负责人；重复通知去重 |
| 预估工作量 | 3 人日 / 2 卡 |
| 人工主导 | 是（人工主导：升级阈值与渠道需业主定） |
| 外部阻塞 | 阻塞于 C-12（SLA 时限与等级） |

## 1. 目标

让超期不需要人盯，系统按时间梯度把责任往上推。

## 2. 输入

- notification 表
- work_order_event
- V1.2 §10.4 升级策略

## 3. 改动范围

- 允许：backend/app/modules/notify/**、workers/notify_worker.py
- 禁止：在业务事务内同步发通知

超出上述范围即视为越权改动，即使代码正确也退回。

## 4. 实现要点

- 通知走 outbox，事务提交后投递，失败重试 3 次后进死信
- 同一工单同一等级只通知一次，用 `dedup_key` 去重
- 阈值 0–24h / 24–72h / >72h 可配置，默认值待业主确认
- 免打扰时段只延迟不丢弃，次日合并为一条摘要

## 5. DoD（可验证的完成定义）

- 超时工单 24h 内产生 1 条通知给 handler+主管
- 72h 后产生考核清单条目
- 重复定时器触发不产生重复通知
- 通知失败不影响状态迁移

## 6. 验收用例

| # | 输入 | 操作 | 期望结果 |
| --- | --- | --- | --- |
| 1 | 工单超期 2 小时 | 定时扫描 | handler 与主管各 1 条通知，dedup_key 相同则只发 1 条 |
| 2 | 超期 80 小时 | 定时扫描 | 新增考核清单条目，渠道按配置 |
| 3 | 通知服务不可用 | 发通知 | 重试 3 次后进死信，工单状态不受影响 |

## 7. 依赖与顺序

T-07 之后；T-16 监控要观测通知失败率。

## 8. 常见坑

- 不要在迁移事务内发消息
- 不要给同一人重复推送同类通知
- 不要忽略夜间免打扰
